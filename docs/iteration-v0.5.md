# 0.5 迭代建议

状态：待实施。0.4.1 完成标题配色和空白区域右键菜单修正；本文件不代表下列能力已接通。

## 目标与优先顺序

用户要的是可以自由调整、持续推进的编码工作流。目前已有持久化计划、修复验收和非阻塞管理，但对现有计划的修改仍依赖表单，真实主模型的规划与回顾还未完成整体实测。建议 0.5 优先解决这两个断点，再接真实通讯渠道。

### 一、用自然语言调整当前计划

输入区明确区分“新目标”和“补充当前计划”，显示目标会话及计划，避免一句补充意外生成独立计划。现有开始、暂停、取消按钮保持可直接使用。

主 Agent 接收已有计划的目标、已完成结果及版本号，输出后续节点调整建议。桌面展示增删改摘要；用户应用后仍走现有 `patch_plan` 的校验与事务，不给模型新的直接写入权限。

只修改尚未开始节点，允许追加修复和验收。运行状态变化导致版本过期时，不能静默覆盖；保留补充要求并允许基于最新版本重新生成建议。耗时理解和建议生成不能阻塞已有任务及结构化管理指令。

验收示例：计划执行时输入“先补回归测试，再继续界面修改”，建议只改变后续工作，保持已完成节点、角色快照、预算和回调来源。

### 二、验证真实主 Agent 的完整执行闭环

目前的真实 Codex 实测采用确定性规划与回顾。新增显式启用的端到端实测，用配置的真实主模型生成计划、读取实际失败、提出修复和验收，再由 Codex 执行。

继续使用隔离小项目，验证目标中途补充、暂停恢复、失败修复、最终回调；保存脱敏的执行摘要和实际证据。该测试与默认 CI 夹具分开，默认 CI 不使用云端额度。

验收要求：主模型不能靠完成文字通过失败节点；只有有效的修复关系和实际验收命令证据允许父计划完成。预算耗尽、模型异常或用户取消必须停在可解释的状态。

### 三、补充可检查的项目变更

把现有“更改”面板接到真实项目状态，支持查看改动文件和 diff，与任务、命令结果相邻展示。已有用户改动必须保留，界面明确区分项目当前改动与能够确认的任务增量，不能把工作区全部变化都归给 Agent。

验收要求：项目包含未提交修改时能正确展示；不执行 reset、自动提交或覆盖用户文件；非 Git 项目明确说明可用信息。

## 后续：首个真实通讯渠道

建议作为紧随其后的独立迭代，复用 0.5 的“补充当前计划”语义，让桌面与远程使用同一种指令：

- 渠道适配器统一接收消息 ID、发送者、会话、回复关联和正文；不把平台字段渗入调度核心。
- 完成身份配对、入口到本地会话的绑定、列出与切换会话，防止发错项目。
- 同一消息重复投递只处理一次，主 Agent 接收后立即确认，子任务继续异步执行。
- 子任务与最终计划分别回到最初渠道和会话；通知失败独立重试，不重复执行任务。
- 先接一个明确选定的平台，测试断连、重连、消息重复、切换会话和回调失败，再扩展其他渠道。

H5／App 在渠道鉴权与远程管理协议稳定后复用同一服务；本轮不增加公网监听或移动端外壳。
